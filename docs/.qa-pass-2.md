## SIGNIFICANT

### 1. The pass-1 revision prescribed a fix that does not work — found, reproduced, rewritten

`contributing.md`'s new exception blockquote told a contributor to "give the
`@media (pointer: coarse)` block its own `/* ---- … ---- */` section header so the
parser stops filing `.cui-input` under Select — then rebuild, and the diff you commit
contains only your work plus the corrected Select line."

I re-implemented `extractPrimitives()` and ran it. That is false. Inserting
`/* ---- Touch sizing ---- */` above the media query yields:

```
+ ('Select', ['cui-select'])            # fixed
+ ('Touch sizing', ['cui-input', 'cui-select'])   # NEW, wrong
- ('Select', ['cui-select', 'cui-input'])
```

The misattribution goes away and a **fabricated "Touch sizing" primitive** takes its
place in the agent's prompt. Net: a different wrong line, shipped into generation.
This is the most consequential thing pass 2 found, and pass 1 did not catch it
because pass 1 only reproduced the *symptom*, never the proposed cure.

Fixed: Known gap 2 now lays out both candidates, marks the header approach as a trap
with the reproduced output, and names the real fix — make `extractPrimitives()`
strip `@media { … }` bodies before matching, ~5 lines in `scripts/build.mjs`. The
`:82` blockquote no longer prescribes a cure; it defers to Known gap 2.

### 2. The accessibility mitigation misquoted the shell's own ring — in the weaker direction

`components.md` claimed the ConjureOS shell puts back a ring with
`box-shadow: 0 0 0 3px var(--cui-accent-tint)` and told readers the shell "does
exactly this." Source says otherwise: `ConjureOS/src/shell/ui/app.css:1192-1200`
uses **`--cui-accent-mute`** (`rgba(124,106,247,0.18)`), not `--cui-accent-tint`
(`0.28`), and also sets `border-color` and a `background-color` shift.

Why it matters beyond pedantry: the misquote appeared inside advice about fixing an
accessibility defect, and it recommended copying a ring **fainter** than the one the
docs named. Fixed — the shell rule is now quoted verbatim with its line range, and
the text says plainly that `--cui-accent-tint` is the higher-contrast choice if you
are copying it for accessibility rather than for visual parity.

### 3. The mitigation snippet silently eats two of the library's own shadows

The recommended `:focus-visible` rule uses `box-shadow`. `box-shadow` is a single
property, so while focused it **replaces** `.cui-card--interactive`'s hover lift
(`--cui-shadow-accent`, `src/ui.css:56`) and `.cui-tab--active`'s glow (`:526`).
Nobody had said so. Caveat added under the snippet, with the shell-double-ring
warning alongside it.

### 4. Rendering is still unverified — and that gap is now partially closed, not closed

No browser was opened in this pass either. Every "what it looks like" claim is still
read from CSS. I did close the WCAG half numerically: computing relative luminance
for the status hexes against `#ffffff` gives `--cui-success` **1.92:1**,
`--cui-warn` **1.67:1**, `--cui-error` **2.77:1** (vs ≥6.9:1 on the dark
`--cui-bg` they were designed for). Those measured numbers replaced the hand-wavy
"low-contrast on white" in `tokens.md`. The focus-indicator verdicts in
`components.md` remain *reasoned* — a 1px `border-color` change is asserted to fail
WCAG 2.4.11 rather than measured against the spec's area and change-of-contrast
tests. That assertion is very likely right and matches issue #4's own framing, but
it is not a measurement, and the docs should not be read as if it were.

components 18, usage 6, contributing 9), and **every one is preceded by an explicit
