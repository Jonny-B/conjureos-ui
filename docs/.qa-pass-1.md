# QA pass 1 — adversarial review of `conjureos-ui/docs/`

Reviewed 2026-08-21 against `@conjureos/ui` @ `83d4dcc` (v0.3.1), plus ConjureOS,
conjureos-pack, conjureos-fitness, conjureos-app-recipes at their working-tree state.

Headline: this is an unusually accurate documentation set. Token enumeration, class
enumeration, all five consumption paths, and all three self-reported defects check out
against source. The failures below are concentrated in two places: the light/dark
retheme guidance in `tokens.md` (materially wrong, will ship broken UI) and a handful of
self-contradictions between files.

---

## BLOCKERS

### B1. `tokens.md` undercounts hardcoded values by ~7; the light-theme recipe ships broken UI

**Location:** `tokens.md:290-291` ("nothing hardcodes a hex except five deliberate
cases") and `tokens.md:314-319` (the five-item "known rough edges" list), plus the
worked `@media (prefers-color-scheme: light)` snippet at `tokens.md:294-312`.

**What is wrong:** the claim of five hardcoded cases is false, and the five named are not
the ones that most break a light theme. Literal colors in `src/ui.css` that will NOT
follow a token override:

| Source | Literal | In the doc's list of five? |
|---|---|---|
| `src/ui.css:106,148,153,169,174` | `color: white` on `--primary`/`--danger`/`--info` | yes |
| `src/ui.css:159` | `color: #1a1206` on `--warning` | yes |
| `src/ui.css:368` | `%239ca3af` chevron stroke in the data-URI | yes |
| `src/ui.css:485` | `background: white` on the checked toggle thumb | yes |
| `src/ui.css:212-217` | **8 literals** — `rgba(52,211,153,0.14/0.35)`, `rgba(251,191,36,…)`, `rgba(248,113,113,…)`, `rgba(239,68,68,…)` — the fills AND borders of `--success`/`--warn`/`--error`/`--danger` pills | **NO** |
| `src/ui.css:522-527` | `.cui-tab--active` gradient `rgba(124,106,247,0.55)`/`rgba(74,158,255,0.4)`, `box-shadow rgba(124,106,247,0.25)`, `color: white` | **NO** |
| `src/ui.css:569` | `.cui-modal-backdrop` `rgba(0,0,0,0.6)` | **NO** |

**Evidence of the internal contradiction:** `components.md:503-521` ("Hardcoded values")
already lists every one of these correctly — including the pill row (`:512`), the
`--tab--active` row (`:517`), and the backdrop row (`:518`). `tokens.md` links to that
exact section while summarizing it as "five deliberate cases."

**Consequence:** a developer who follows `tokens.md:294-312` verbatim gets a light
surface with dark-tuned pill tints (0.14-alpha status fills on a white card are close to
invisible), a purple-on-white active tab, and a 60%-black modal scrim over light chrome.
The doc's own conclusion ("this mostly works") is not supportable.

**Should say:** replace "five deliberate cases" with a pointer to the full
`components.md` table and enumerate the retheme-blocking subset explicitly: status-pill
tints, the active-tab gradient + glow, the modal backdrop, plus the four already listed.
Downgrade "this mostly works" to "backgrounds/foregrounds/borders follow; pills, active
tabs and the modal scrim do not."

### B2. `usage.md` gotcha 10 states the opposite of what `demo.html` does

**Location:** `usage.md:268-271`.

**Doc says:** "`dist/` is gitignored… otherwise `demo.html` pointed at `./dist/ui.css`
shows an unstyled page."

**Evidence:** `demo.html:14` is
`<link rel="stylesheet" href="https://unpkg.com/@conjureos/ui/dist/ui.css" />`, with a
header comment at `demo.html:9-11` explaining the choice. `usage.md:64` says so itself
("this is what `demo.html` does"), and `contributing.md:94-97` says so a third time.

**Consequence is worse than a typo, and inverted from what the doc implies:** because
the committed demo pulls the **unpinned latest published** package from a CDN, a
maintainer who edits `src/ui.css`, runs `npm run build`, and opens `demo.html` sees *no
change at all* — the page is rendering npm's copy, not `dist/`. That is a live trap for
the exact "verify a change" loop `contributing.md:91-104` prescribes.

**Should say:** gotcha 10 should be about `dist/` being missing for the ConjureOS Vite
plugin only, and should state that `demo.html` renders the published CDN build, so local
changes are invisible there until you temporarily repoint the `<link>` (as
`contributing.md:94` already instructs).

## SIGNIFICANT

### S1. `components.md` Input and Select sections state 14px with no touch caveat

**Location:** `components.md:259-262` (Input) and `components.md:321-324` (Select).

**Evidence:** `src/ui.css:388-393` bumps both to `16px` under `@media (pointer: coarse)`.
The behavior is documented in three other places (`components.md:521` hardcoded table,
`usage.md:255-259`, `docs/README.md:145-147`) but not in the two class-reference sections
a developer actually reads when styling a form. `components.md:260` flatly says "14px".

**Should say:** add one line to each section: "14px on desktop; 16px under
`@media (pointer: coarse)` — see gotcha 7 before overriding `font-size`."

### S2. `docs/README.md` mis-states how anchor apps consume the package

**Location:** `docs/README.md:70-71` — "Anchor apps consume it (`conjureos-app-recipes`,
`conjureos-fitness`) as an ordinary npm dependency."

**Evidence:** `conjureos-app-recipes/package.json:357` has `@conjureos/ui: ^0.1.2` under
**devDependencies** (verified: `dependencies` entry is absent), and the app imports a
vendored copy — `conjureos-app-recipes/src/conjureos-ui.css:1-5` ("VENDORED COPY … DO NOT
EDIT BY HAND") built from v0.1.2, pulled in at `src/main.tsx:13` with
`document.body.classList.add("cui-ui")` at `:25`. Only `conjureos-fitness` matches the
README's description (`package.json` `dependencies: ^0.1.1`, `src/main.tsx:9`,
`index.html:8`).

`usage.md:164-188` gets this exactly right. The README contradicts it.

**Should say:** "one as an ordinary npm dependency (`conjureos-fitness`), one as a
devDependency with the CSS vendored into `src/` (`conjureos-app-recipes`, because the
store bundler externalizes bare imports) — see usage.md path 4."

### S3. `tokens.md` attributes `--cui-radius-lg` to hero cards; hero cards do not use it

**Location:** `tokens.md:213` — "`--cui-radius-lg` | `14px` | Hero cards, modals".

**Evidence:** `src/ui.css:59-63`, `.cui-card--hero`, sets only `background`,
`background-blend-mode`, and `border-color`. It inherits `.cui-card`'s
`border-radius: var(--cui-radius)` (10px) from `:40`. `--cui-radius-lg` is consumed by
exactly one rule: `.cui-modal` at `:583`. `components.md:98-102` describes the hero card
correctly.

**Should say:** "Modals. (Not consumed anywhere else; `.cui-card--hero` keeps the 10px
default.)"

### S4. Nothing documents that the wrapper element itself cannot carry a primitive class

**Location:** absent from all five files. `components.md:6-8` comes closest ("requires an
**ancestor** with `class="cui-ui"`") but never states the failure mode.

**Evidence:** every rule in `src/ui.css` is a descendant selector — `.cui-ui .cui-thing`
(601 lines, no exceptions; `grep -c '^\.cui-ui \.' ` matches every primitive rule). So
`<body class="cui-ui cui-stack-v">` silently applies no stack, and
`<div class="cui-ui cui-card">` renders no card. This is the single most natural mistake
for someone adopting the library on a sub-tree rather than on `<html>`.

**Should say:** one explicit line in `components.md`'s preamble and in `usage.md`
Gotchas: the wrapper class and the primitive class can never be on the same element.

### S5. Nothing warns that the wrapper paints `background` on itself only

**Location:** `tokens.md:17-23` and `docs/README.md:129` both list
`background: var(--cui-bg)` as part of the wrapper baseline, but no doc states the
consequence.

**Evidence:** `src/tokens.css:149-154` applies `color` + `background` to the
`.cui-tokens, .cui-ui` element. If that element is a `<div>` rather than `<html>`/`<body>`,
the page canvas outside it stays the UA default white — visible as white gutters,
white overscroll on iOS, and a white flash before paint.

**Should say:** "put the wrapper on `<html>` or `<body>`; on a nested element the page
canvas outside it is unstyled."

### S6. `contributing.md`'s build instruction and its own known-gap advice are in direct conflict

**Location:** `contributing.md:82` ("**Always run `npm run build` and commit the
resulting `MODERN_WHIMSY.md` diff.**") vs `contributing.md:274-277` ("Do that with the
next release rather than as a drive-by").

**Evidence:** I reproduced `extractPrimitives()` against the current `src/ui.css`. Output
differs from the committed `MODERN_WHIMSY.md` AUTOGEN block on exactly one line:

```diff
-- Select: `cui-select`
+- Select: `cui-select`, `cui-input`
```

So any contributor who follows `:82` today commits a wrong line into the file that is
compiled into the Dev agent's prompt (`devPromptV2.ts:16`). The doc knows this
(`:261-277`) but does not reconcile the two instructions.

**Should say:** at `:82`, "…and commit the diff — **except** the known stale `Select`
line, see Known gap 2; fix the section header first."

### S7. `~40 primitive classes` is short by five

**Location:** `docs/README.md:31`, `contributing.md:12`.

**Evidence:** `grep -oE '\.cui-[a-zA-Z0-9_-]+' src/ui.css | sort -u` returns 46 names,
45 excluding the `.cui-ui` wrapper itself. `components.md:16-31` correctly enumerates all
45. "~40" reads as an estimate, but the two files that state a count state a low one
while `components.md` claims completeness.

**Should say:** "45 primitive classes."

### S8. Accessibility — the missing focus rings are a real defect, not just an omission

**Verification:** `grep -n focus src/ui.css` returns focus styling at only four places:
`:272` (`.cui-input:focus`, border-color only), `:374` (`.cui-select:focus`, border-color
only), `:430` (`.cui-slider:focus::-webkit-slider-thumb`), `:488`
(`.cui-toggle input:focus-visible`). There is **no** `:focus`/`:focus-visible` rule on
`.cui-button`, `.cui-chip`, `.cui-card--interactive`, or `.cui-tab`. The docs' non-goals
claim (`components.md:527-528`) is accurate.

**But the framing understates it.** These are not obscure primitives — `.cui-button` is
used by the ConjureOS shell itself, and `.cui-tab`/`.cui-chip` are rendered as `<button>`
in the docs' own examples (`components.md:244-246`, `:410-412`). The UA default outline
survives only because no rule sets `outline: none` on them, which makes keyboard
visibility an accident of the absence of a reset rather than a decision. Meanwhile
`.cui-input`/`.cui-select` DO set `outline: none` (`src/ui.css:268`, `:366`) and replace
it with a 1px border-color change — a contrast delta that will not meet WCAG 2.4.11
non-text contrast on its own. `components.md:281-284` flags this and recommends the
shell's glow ring; that mitigation should be promoted from an advisory blockquote to a
stated package limitation, and ideally filed as an issue against the package rather than
left as consumer homework.

**Should say:** keep the non-goal list, but add a short "Accessibility status" section
stating plainly: four of the eleven interactive primitives have a focus indicator; two of
those suppress the UA outline and replace it with a sub-3:1 border change; five have
none. Link a tracking issue.
